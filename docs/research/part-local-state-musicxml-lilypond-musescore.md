# Part-Local State in MusicXML, LilyPond, and MuseScore

**Context:** Wayfinder research ticket [#104: Research part-local state across MusicXML, LilyPond, and MuseScore](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/104). This report records source findings only; it does not choose this renderer's policy.

## MusicXML 4.0 requirements

The normative sources are the [MusicXML 4.0 reference](https://www.w3.org/2021/06/musicxml40/musicxml-reference/) and its [XSD](https://www.w3.org/2021/06/musicxml40/listings/musicxml.xsd/), published 1 June 2021. In `score-partwise`, each `<part>` contains its own sequential `<measure>` elements; each measure contains an ordered, interleaved `music-data` stream. Thus an `<attributes>` event belongs to that part's stream. Its changes take effect in musical score order, including mid-measure, rather than being applied by a document-wide pass over element types. The XSD orders children within one `<attributes>` element (including divisions, keys, times, clefs, and transpositions), but that child order does not merge state between parts. See [`score-partwise`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/score-partwise/), [`measure`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/measure-partwise/), [`attributes`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/attributes/), and XSD `music-data`.

- **Divisions:** `<divisions>` is units per quarter note for note, backup, and forward durations. It is in the part's attributes stream and can change as that stream proceeds; it has no staff-number selector, so it is the duration scale for that part's stream, not a cross-part shared scale. [`divisions`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/divisions/), [`duration`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/duration/), [`backup`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/backup/), [`forward`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/forward/).
- **Key, time, and clef:** each is part-local by containment and may have a `number` staff selector. When omitted, it applies to all staves in that part; when present, it targets the specified staff. These are not score-global merely because parts share measure numbers. See [`key`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/key/), [`time`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/time/), [`clef`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/clef/), and the XSD `staff-number` attributes.
- **Transposition:** `<transpose>` is the interval added to written pitch to obtain sounding pitch. It is part-local, can target one staff using `number`, and without that selector applies to all staves in the part. A later transposition change occurs at its score-order position. [`transpose`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/transpose/).

These are the interchange format's scope and ordering rules, not requirements that every application preserve or render every legal construct.

## Program behavior (separate from the specification)

### LilyPond 2.24.4

The official [2.24 notation reference: pitches](https://lilypond.org/doc/v2.24/Documentation/notation/pitches) documents clefs, key signatures, and `\transpose`; the [rhythms reference](https://lilypond.org/doc/v2.24/Documentation/notation/rhythms) documents `\time`. In a normal score, each `\new Staff` is a distinct context and these commands affect the context receiving the music, so differing staff state can be expressed independently. `\transpose` transforms the enclosed music expression (including a key signature when one is specified); it is not a score-wide persistent transposition inferred from the instrument label. LilyPond contexts and engraver placement are configurable, so shared/custom contexts can change how state is propagated or displayed; the default-context observation is not a universal guarantee for every user layout. The implementation/documentation snapshot is tag `v2.24.4`, commit [`b7908403efe0761cec86c94db0c529db031246a0`](https://github.com/lilypond/lilypond/tree/b7908403efe0761cec86c94db0c529db031246a0).

### MuseScore Studio 4.4.4

The official [MuseScore source at tag `v4.4.4`](https://github.com/musescore/MuseScore/tree/22326704eef99117039391decab233a8b1c2ae19) models key events, clefs, and time signatures on `Staff` (`keyList`, `clefList`, `m_timesigs`; see [`staff.h`](https://github.com/musescore/MuseScore/blob/22326704eef99117039391decab233a8b1c2ae19/src/engraving/dom/staff.h) and [staff time lookup](https://github.com/musescore/MuseScore/blob/22326704eef99117039391decab233a8b1c2ae19/src/engraving/dom/staff.cpp#L708-L719)). Each staff can therefore retain its own timeline. Instrument transposition is separately represented by an `Instrument` interval ([`instrument.h`](https://github.com/musescore/MuseScore/blob/22326704eef99117039391decab233a8b1c2ae19/src/engraving/dom/instrument.h)), while the part owns its staff collection ([`part.h`](https://github.com/musescore/MuseScore/blob/22326704eef99117039391decab233a8b1c2ae19/src/engraving/dom/part.h)). These are implementation data structures, not MusicXML conformance promises.

The same pinned MusicXML importer demonstrates narrower behavior than the internal model: its `transpose(partId, tick)` stores intervals by part and does not read the MusicXML `<transpose number>` attribute; its `time(cTime)` updates a score-wide signature map and does not read a staff selector. The divisions parser writes an importer-held `m_divs`; `initPartState` does not reset it between parts. These code paths mean staff-targeted MusicXML transposition/time and omitted divisions at a part boundary warrant caution when predicting import results. This report does not claim a runtime reproduction or characterize every later import/export pass. Relevant source: [`importmxmlpass1.cpp`](https://github.com/musescore/MuseScore/blob/22326704eef99117039391decab233a8b1c2ae19/src/importexport/musicxml/internal/musicxml/importmxmlpass1.cpp#L269-L275), [attributes/clef/time/transpose/divisions parsing](https://github.com/musescore/MuseScore/blob/22326704eef99117039391decab233a8b1c2ae19/src/importexport/musicxml/internal/musicxml/importmxmlpass1.cpp#L2685-L2912).

MuseScore handbook material is maintained separately from that source tag; this comparison pins source behavior to 4.4.4 and does not assume current handbook wording exactly describes that release.

## Limits

- The MusicXML baseline is the 4.0 report/XSD only; this does not compare later editions or `score-timewise` serialization.
- LilyPond's documented syntax is not a specification for all possible custom context/engraver configurations.
- MuseScore claims are limited to inspected 4.4.4 source paths. The importer observations are code-path evidence, not a complete conformance test, and may differ in later releases or other import paths.
- No sample score was used to test either application's rendered output. The sources do not settle every ambiguity of malformed or underspecified input, nor do these findings select renderer behavior.
