# MusicXML 4.0 `score-partwise` Feature Inventory

**Context:** Wayfinder research ticket [#67: Inventory MusicXML 4.0 score features and dependencies](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/67).

## Scope and reading

This inventory is about score content a `score-partwise` renderer may need to interpret or lay out. It maps feature families, their dependencies, and schema ordering; it does not select product priority or imply that every construct must be supported. “Renderer-relevant” includes both visible notation and data that affects score traversal, placement, or playback but may not itself be drawn.

The governing sources are the W3C Music Notation Community Group's **MusicXML 4.0 Final Community Group Report (1 June 2021)**, its element reference, and its XSD. The reference describes meaning; the XSD defines permitted element structures, child order, cardinalities, data types, and enumerations. Schema permission alone does not establish visual behavior or require an application to implement a feature.

The element reference is the catalog for the full set of score constructs; the families above group related material for renderer analysis rather than enumerate every leaf element. In particular, attributes such as placement, positioning, formatting, print-object, and playback data appear across many element types and are governed by the individual reference entries and schema types.

## Structural dependencies and ordering

### Document and part structure

The `score-partwise` content model is ordered: optional `work`, movement number/title, identification, and defaults; zero or more credits; the required part list; then one or more parts. A part contains one or more measures. The part list's ordering establishes vertical part order, while its IDs connect definitions to musical part data. These are structural facts from the [`score-partwise`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/score-partwise/) and [`part-list`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/part-list/) references and the [MusicXML 4.0 XSD](https://www.w3.org/2021/06/musicxml40/listings/musicxml.xsd/).

### Measure content and score order

The schema's `music-data` group permits a repeated, interleaved choice of `note`, `backup`, `forward`, `direction`, `attributes`, `harmony`, `figured-bass`, `print`, `sound`, `listening`, `barline`, `grouping`, `link`, and `bookmark`. Therefore there is not one global measure sequence such as “all attributes, then all notes, then all directions.” The order actually present in the measure matters: attribute changes and directions can occur between events, and cursor movement affects the position of later events. A renderer must process the permitted sequence rather than reorder it by element family. See the [XSD `music-data` and `measure` definitions](https://www.w3.org/2021/06/musicxml40/listings/musicxml.xsd/) and the [`measure`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/measure-partwise/) reference.

`attributes` has its own ordered child model (divisions, keys, times, staves/part symbol/instruments, clefs, staff details, transpositions, and measure styles, subject to the schema's optionality and repetitions). A `note` likewise has an ordered child model and constrained alternatives: grace/cue status with pitch, unpitched pitch, or rest; then duration/ties and the applicable instrument, voice, type, dot, accidental, time modification, stem, notehead, staff, beam, notation, lyric, and playback content. The XSD, rather than a renderer-specific expectation about a common export, is authoritative for exact child sequence and occurrence constraints.

### Time, voice, and state dependencies

- `divisions` defines duration units per quarter note. A note's duration is not a wall-clock value and is meaningful only in the active divisions context. `backup` and `forward` use the same score-time scale to move the measure cursor.
- The `<chord/>` marker places a note at the onset of the preceding non-chord note; it does not advance the cursor separately. Grace notes have different duration requirements than ordinary notes. Voices/staff assignments and cursor movement together represent multiple simultaneous streams.
- Musical attributes are score-order state: key, time, clef, staff setup, transposition, and similar changes apply where encoded and inform subsequent events. Mid-measure changes cannot safely be detached from their position in the sequence.
- Numbered start/stop/continue notation (for example ties, slurs, tuplets, wedges, pedals, octave shifts, and endings) creates relationships across event boundaries; layout may need to retain those relationships through measure and system breaking.
- A measure can carry explicit internal or end barlines. Time signature and duration totals alone do not specify a renderer rule for inserting unencoded barlines. The `measure` and [`barline`](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/barline/) references define explicit structural data; interpretation of anomalous meter/duration totals is a separate product policy.

## Score features versus XML infrastructure

These layers should not be conflated:

1. **XML processing:** byte decoding and XML declaration handling, XML syntax and entity/reference processing, and namespace handling when applicable belong to the XML processor. XML 1.0 defines well-formedness and processor requirements; it does not make those requirements engraving features. See [XML 1.0 §2.1](https://www.w3.org/TR/xml/#sec-well-formed), [§4](https://www.w3.org/TR/xml/#sec-physical-struct), and [§4.3.3](https://www.w3.org/TR/xml/#charencoding).
2. **MusicXML structural conformance:** the MusicXML XSD specifies legal structure, order, cardinality, lexical forms, and types for schema validation. Validation can catch malformed or out-of-schema score data, but passing validation does not mean a renderer supports or draws every construct. The official edition provides the [XSD listing](https://www.w3.org/2021/06/musicxml40/listings/musicxml.xsd/) alongside the [reference](https://www.w3.org/2021/06/musicxml40/musicxml-reference/).
3. **Renderer feature support:** deciding which valid constructs to interpret, preserve, ignore with a warning, reject, lay out, or render is a separate product contract. This report makes no support or priority decision.

Parser security/resource limits, diagnostics and source locations, DTD/entity resolver policy, unsupported encodings, and whether to run XSD validation are implementation/conformance-profile questions. They affect safe and predictable input handling, not the score-feature inventory. XML well-formedness or schema validation should not be described as visual feature support.

## Limits of the sources

- The MusicXML 4.0 sources are the official W3C Community Group Report dated 1 June 2021 and its matching reference/XSD snapshot. This report does not establish whether a later MusicXML edition has superseded it; the request is specifically about 4.0.
- The specification describes interchange structures and semantics, not renderer architecture, product priority, exact visual equivalence, or acceptance criteria. It does not require a renderer to draw every construct merely because the schema permits it.
- The scope is `score-partwise`. `score-timewise`, container/compressed-file packaging, opus documents, and sound-set implementation details are not inventoried as alternative document workflows.
- A schema-validity claim requires actually validating against the chosen schema and processor profile. This report uses the published schema as a source for content models and does not claim to validate any score document.
