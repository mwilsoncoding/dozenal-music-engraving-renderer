# Rust MusicXML Parser Options

Research for [Assess Rust MusicXML parser options against the MVP subset](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/8). The ticket is the context pointer; this report does not claim or resolve it.

## MVP Context

Input is uncompressed MusicXML, one file per CLI invocation, with one part and one independent voice. Accept monophony first and stacked chords as required, rests, representable meters, ties, integer-semitone alterations from double-flat through double-sharp normalized to concert pitch after declared transposition, octaves 0-9, whole through 64th notes plus dotted quarter and dotted half, and explicit beam groups (individual flags when beam data is absent). Reject tuplets, repeats, grace notes, percussion, unsupported durations or constructs, and malformed input with helpful context. Do not read `.mxl` archives or silently widen this subset.

## Candidates

### Generic XML libraries

[`roxmltree` 0.21.1](https://docs.rs/roxmltree/0.21.1/roxmltree/) builds a read-only tree and exposes namespace-aware names, node source ranges, source-position lookup, and parse-error positions ([`Node`](https://docs.rs/roxmltree/0.21.1/roxmltree/struct.Node.html), [`Document`](https://docs.rs/roxmltree/0.21.1/roxmltree/struct.Document.html), [`Error`](https://docs.rs/roxmltree/0.21.1/roxmltree/enum.Error.html)). This gives an application a direct way to validate an explicit allowlist and report element/source context. It is not streaming and implements no MusicXML score semantics: the project must build the MusicXML-to-score mapping, including pitch normalization, transposition, durations, beams, and ties. The crate declares Rust 1.60.

[`quick-xml` 0.42.0](https://docs.rs/quick-xml/0.42.0/quick_xml/reader/struct.Reader.html) is an event-based reader; [`NsReader`](https://docs.rs/quick-xml/0.42.0/quick_xml/reader/struct.NsReader.html) resolves namespaces, and the reader exposes byte positions. This can bound parser memory, but the application must maintain MusicXML state, an allowlist, score mapping, and location-aware diagnostics (including converting byte offsets to line/column if desired). It provides XML rather than MusicXML semantics. The crate declares Rust 1.86. Neither generic library handles `.mxl` archives; the CLI should reject compressed input rather than route it through an archive reader.

### MusicXML-aware libraries

[`acorde-io` 1.2.17](https://docs.rs/acorde-io/1.2.17/acorde_io/) is the most feature-rich actively updated dedicated option evaluated. Its parser builds an `acorde_core::Score`, uses `quick-xml` 0.41, and has bounded input/depth limits; source includes handling for chords, ties, beams, transposition, tuplets, grace notes, and percussion ([parser](https://docs.rs/crate/acorde-io/1.2.17/source/src/musicxml/parser.rs), [manifest](https://docs.rs/crate/acorde-io/1.2.17/source/Cargo.toml)). It requires Rust 1.87 and introduces the `acorde-core` model, so integration requires adapting that model or adopting it. The parser's event match has catch-all paths rather than a reject-unknown contract, and some malformed pitch fields fall back to defaults; XML errors are wrapped as strings without a MusicXML element path or source location. Treat it as a candidate only if a strict pre-validation layer or upstream changes can reject unsupported/malformed content and provide useful locations.

[`music21-rs` 0.8.0](https://docs.rs/music21-rs/0.8.0/music21_rs/) has a substantial MusicXML importer and returns its own score/stream model. The published importer accepts `score-partwise` and its documentation explicitly says content it does not model is passed over; its XML tree/parser is custom code, and its public XML/MusicXML errors carry string messages rather than source positions ([reader](https://docs.rs/crate/music21-rs/0.8.0/source/src/musicxml/read.rs), [XML parser](https://docs.rs/crate/music21-rs/0.8.0/source/src/xml.rs), [errors](https://docs.rs/crate/music21-rs/0.8.0/source/src/error.rs)). Its broad semantics may save mapping work, but pass-over behavior conflicts with strict rejection unless wrapped, and conversion from its score model remains necessary. The published crate declares Rust 1.90.

[`musicxml` 1.1.2](https://docs.rs/musicxml/1.1.2/musicxml/) has partwise/timewise types and a dedicated parser, but the published version and latest observed upstream commit are both from 2024-11-05. Its handwritten parser/model use string errors, and its note parser ignores unrecognized children ([parser](https://docs.rs/crate/musicxml/1.1.2/source/src/parser/xml_parser.rs), [note source](https://docs.rs/crate/musicxml/1.1.2/source/src/elements/note.rs)). No current maintenance evidence was found in the registry or repository history checked for this report. Its `.mxl` support is irrelevant to the uncompressed-only policy and must not be enabled by the CLI.

## Conditional Recommendation

For a small, deliberately strict subset where contextual rejection matters more than streaming, evaluate `roxmltree` first as the XML substrate and map accepted elements into a renderer-owned score model. A single input per invocation does not by itself justify the extra state and diagnostic work of a streaming parser. Use `quick-xml` instead if a measured memory/input-size constraint requires streaming; budget additional work for event state and source-location tracking.

If reusing a broad score model is more valuable, evaluate `acorde-io` against the same fixtures before considering adoption. Its active maintenance and MusicXML coverage may reduce semantic mapping, but do not adopt it without proving strict unsupported-element rejection, malformed-value errors, pitch/transposition normalization, and useful source context. `music21-rs` has similar strictness/model-conversion risks; the older `musicxml` crate lacks comparable recent maintenance evidence. This is a conditional recommendation, not an implementation selection.

Regardless of parser, validation fixtures must cover accepted monophonic and chord notes, rests, meter, ties, alteration/transposition, octave and duration bounds, explicit/absent beams, plus rejection of extra parts/voices, tuplets, repeats, grace notes, percussion, unsupported constructs/durations, malformed values/XML, and compressed `.mxl`. Define whether both `score-partwise` and `score-timewise` are accepted before choosing a dedicated parser.

## Maintenance Evidence and Uncertainties

Checked against crates.io metadata and upstream default-branch commits on 2026-10-02. `roxmltree` 0.21.1 was published 2025-10-12; latest observed upstream commit was 2026-09-22 ([crate](https://crates.io/crates/roxmltree/0.21.1), [commit](https://github.com/RazrFalcon/roxmltree/commit/3f5c78dea576)). `quick-xml` 0.42.0 was published 2026-08-22; latest observed commit was 2026-09-02 ([crate](https://crates.io/crates/quick-xml/0.42.0), [commit](https://github.com/tafia/quick-xml/commit/2eaa844b4b40)). `acorde-io` 1.2.17 was published 2026-09-28; latest observed commit was 2026-09-28 ([crate](https://crates.io/crates/acorde-io/1.2.17), [commit](https://github.com/kent-tokyo/acorde/commit/5ebd69be5bd0)). `music21-rs` 0.8.0 was published 2026-10-01; latest observed commit was 2026-10-02 ([crate](https://crates.io/crates/music21-rs/0.8.0), [commit](https://github.com/float3/music21-rs/commit/9550b658c4b7)). `musicxml` 1.1.2 was published 2024-11-05, with no later commit observed ([crate](https://crates.io/crates/musicxml/1.1.2), [commit](https://github.com/hedgetechllc/musicxml/commit/79271853ae3e)). These dates establish observed activity, not guarantees of future maintenance.

Unresolved: the accepted MusicXML root form (`score-partwise`, `score-timewise`, or both); the diagnostic contract for "helpful contextual errors" (line/column, element path, measure/note); fixture coverage from real exporters; and whether the project toolchain meets the dedicated crates' declared Rust versions. Namespace-prefixed XML and each dedicated parser's treatment of unusual but valid XML also need fixture tests. No parser's strictness should be inferred from MusicXML support alone.
