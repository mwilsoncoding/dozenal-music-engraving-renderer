# Rust Property Testing for the Parser and Renderer

Research for [Research property-based testing for the Rust parser and renderer](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/50). The ticket is the context pointer; this report does not resolve it.

## Context

The README declares `Dependencies: None`, and the [MVP spec](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/21) rules out third-party Rust crates. The current test suite combines CLI-to-SVG integration checks with private parser/rendering unit tests: [integration tests](../../tests/cli_to_svg.rs) already cover acceptance and rejection, spacing, transposition, octave bounds, and SVG properties; [internal tests](../../src/main.rs) cover parsed score and rendering behavior. The custom XML parser is in [src/xml.rs](../../src/xml.rs).

## Options

**proptest** is the strongest fit if the dependency constraint is lifted. Its strategies compose generated values and shrink failures through `ValueTree` ([Strategy](https://docs.rs/proptest/latest/proptest/strategy/trait.Strategy.html)); configuration exposes case counts, RNG seeds, shrink limits, and failure persistence ([Config](https://docs.rs/proptest/latest/proptest/test_runner/struct.Config.html), [failure persistence](https://docs.rs/proptest/latest/proptest/test_runner/enum.FileFailurePersistence.html)). That combination suits constrained, nested MusicXML inputs and repeatable regressions. The crate manifest declares `MIT OR Apache-2.0` ([upstream manifest](https://github.com/proptest-rs/proptest/blob/master/proptest/Cargo.toml)). It still adds a dev dependency and its transitive dependency tree, plus strategy and regression-file maintenance.

**quickcheck** provides `Arbitrary` generation and a `shrink` method ([trait](https://docs.rs/quickcheck/latest/quickcheck/trait.Arbitrary.html)); test and shrink limits are configurable ([TestOptions](https://docs.rs/quickcheck/latest/quickcheck/struct.TestOptions.html)). Its public `Gen::new` accepts a size, not a seed ([Gen](https://docs.rs/quickcheck/latest/quickcheck/struct.Gen.html)); upstream initializes the generator from entropy and prints failing arguments rather than a replay seed ([generator source](https://github.com/BurntSushi/quickcheck/blob/master/src/gen.rs), [tester source](https://github.com/BurntSushi/quickcheck/blob/master/src/tester.rs)). A failure can be replayed by retaining its arguments, but repeatable generated runs need extra project-level handling. The manifest declares `MIT OR Apache-2.0` ([upstream manifest](https://github.com/BurntSushi/quickcheck/blob/master/Cargo.toml)). Its `Arbitrary`/shrink implementations are less direct for trees constrained to this application-specific MusicXML profile.

**Deterministic std-only loops** can enumerate a bounded domain or advance a stateful generator with standard iterator tools such as [`repeat_with`](https://doc.rust-lang.org/stable/std/iter/fn.repeat_with.html) and [`successors`](https://doc.rust-lang.org/stable/std/iter/fn.successors.html). Fixed inputs and iteration order make failures reproducible and CI cost predictable, with no dependency or license review. The tradeoff is no framework-provided shrinking, random exploration, or regression corpus: input design, failure reporting, and minimization remain explicit test code.

All three approaches can have bounded test work: proptest exposes case and shrink limits, QuickCheck exposes test and shrink limits, and std-only loops choose their own finite iteration count. The total cost still depends on each generated score's parse/render cost; favor small structures and fixed budgets in CI. Shrinking a complex score can add work, but often pays for itself by reducing diagnosis time. Top-level crate licenses are not a substitute for reviewing transitive licenses if a dependency is ever approved.

## High-Value Properties

- **XML and MusicXML parsing:** bounded mutations of valid fixture structures preserve accepted-profile rules; malformed or unsupported-profile inputs return contextual errors rather than panic. Keep generated documents within the documented subset, including no-namespace `score-partwise`, one part, and one voice, so failures identify parser behavior rather than arbitrary XML noise.
- **Pitch and transposition:** for supported inputs, normalized tone value stays in `0..12` and octave in `0..=9`; semitone arithmetic uses Euclidean division/remainder across negative and octave-crossing alterations; a transposition followed by its inverse restores pitches when both intermediate and final pitches are in range. Existing tests already cover enharmonic boundaries and chromatic/octave transposition.
- **Layout:** generated supported event sequences have finite coordinates and nonnegative spacing; chronological events remain ordered; the computed viewBox contains emitted geometry. These assertions should encode actual layout invariants, not assume every duration has a globally linear spacing rule.
- **SVG:** rendering the same score is deterministic; element IDs are unique; numeric geometry contains no `NaN` or infinity; output parses as XML; and glyphs remain within the viewBox. Existing integration assertions provide a useful base for these invariants.

## Recommendation

**Defer proptest and quickcheck.** Their shrinking and, for proptest, explicit seed/regression support are useful, especially for generated XML trees, but neither benefit justifies violating the README and MVP's current dependency rule. QuickCheck also needs additional seed/replay discipline for repeatable generated runs.

Use a small deterministic property-style layer in the existing internal tests first: exhaustively sweep the compact pitch/alteration/transposition domain around octave boundaries, then assert finite/in-bounds SVG geometry and unique IDs over a small, explicitly generated set of supported event sequences. Keep loops fixed-size and deterministic; do not build a custom general-purpose property framework or PRNG. If the no-third-party-crates constraint is later lifted and generated structured scores reveal bugs the bounded sweeps miss, trial proptest as a dev-only dependency on one parser property, with a fixed case budget and checked-in regression cases. Reassess dependency policy and the full transitive license tree before that change.

## Engraving-Project Precedent

- MuseScore's unit tests use ordinary GoogleTest/QtTest assertions and many checked reference-file comparisons. For example, beam tests compare generated `.mscx` score data against a reference; separate visual tests generate draw data and PNGs for comparison. This is snapshot-like golden regression coverage, not property-based generation. [Beam reference test](https://github.com/musescore/MuseScore/blob/main/src/engraving/tests/beam_tests.cpp#L120-L144), [line-oriented score reference comparison](https://github.com/musescore/MuseScore/blob/main/src/engraving/tests/utils/scorecomp.cpp#L132-L156), [visual-test runner](https://github.com/musescore/MuseScore/blob/main/vtest/vtest.js)
- LilyPond uses a fixed corpus of `.ly` regression inputs and documents pixel-by-pixel comparison of generated images across revisions. Its own test sources include explicit Scheme assertions for compact mathematical behavior, alongside visual regression inputs. The docs exclude non-repeatable random-note examples from the collated regression suite, which is a useful warning for keeping generated tests reproducible. [Regression suite overview](https://github.com/lilypond/lilypond/blob/master/Documentation/en/contributor/regressions.itexi#L0-L27), [pixel-diff workflow](https://github.com/lilypond/lilypond/blob/master/Documentation/en/contributor/regressions.itexi#L181-L233), [Scheme assertion example](https://github.com/lilypond/lilypond/blob/master/input/regression/other/beat-structure-senza-misura.ly), [non-repeatable snippets](https://github.com/lilypond/lilypond/blob/master/Documentation/snippets/GNUmakefile#L0-L15)
- Targeted source searches found no proptest/QuickCheck/RapidCheck framework use in either repository. This is not proof no custom randomized tests exist, but the documented, visible examples are deterministic fixtures, exact reference comparisons, or explicit assertions.

The Rust Project Primer articles describe the complementary value: snapshots are most useful when reviewing large outputs is easier than encoding every detail in assertions; property tests generate varied inputs and check stable invariants, with shrinking/replay making failures tractable. The project can borrow both ideas without immediately adopting either crate.
