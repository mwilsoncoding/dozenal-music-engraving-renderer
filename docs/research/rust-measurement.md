# Rust Test Measurement and Benchmarking

Research for [issue #51](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/51). The [Rust Project Primer measurement guide](https://rustprojectprimer.com/measure/index.html) is a useful starting overview; the recommendations below ground tool behavior in Rust and framework documentation.

## Recommendation

**Defer a committed benchmark suite.** There is no current performance acceptance target, and the MVP explicitly requires no third-party Rust crates or external runtime tools, including for tests ([MVP issue #21](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/21); the [README](../../README.md) also says “Dependencies: None”). A framework added as a dev-dependency would not ship in the CLI, but would still add third-party crates to the development/test dependency graph, contrary to that rule ([Cargo development dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#development-dependencies)).

If a concrete performance question comes up before that policy changes, use a temporary standard-library timing driver for the release CLI only. Do not check in timing tests, change the crate layout, or gate CI on elapsed time. Reconsider component benchmarks after a bottleneck is identified or the dependency policy changes.

## Options

- **`std::time::Instant`:** A monotonic clock suitable for elapsed-time measurement; it has platform-dependent limitations and does not itself provide sampling, statistics, or regression analysis ([`Instant`](https://doc.rust-lang.org/std/time/struct.Instant.html)). A local driver can warm up, collect repeated durations, and calculate a median and median absolute deviation using only `std`. [`black_box`](https://doc.rust-lang.org/std/hint/fn.black_box.html) is only a best-effort optimization barrier, not a guarantee that work cannot be optimized away; it is not needed to time a subprocess.
- **`cargo bench`:** The command builds and runs benchmark targets using the `bench` profile and, by default, libtest's benchmark harness ([Cargo `bench`](https://doc.rust-lang.org/cargo/commands/cargo-bench.html), [profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)). The built-in `#[bench]` API remains unstable, so the command alone does not provide a stable standard-library statistical benchmark harness ([Rust Unstable Book: `test`](https://doc.rust-lang.org/unstable-book/library-features/test.html)). A custom `harness = false` target can run stable Rust, but then the project owns the timing, statistics, output, and comparison logic.
- **Criterion:** Provides warm-up and measurement phases, repeated samples, statistical estimates, and comparison with saved baselines ([getting started](https://bheisler.github.io/criterion.rs/book/getting_started.html), [warm-up](https://bheisler.github.io/criterion.rs/book/user_guide/warm_up_time.html), [measurement time](https://bheisler.github.io/criterion.rs/book/user_guide/measurement_time.html)). It is the strongest general-purpose choice if the crate policy is relaxed, but requires a dev-dependency and its transitive dependencies. It should not be added under the present MVP rule.
- **Divan:** Another stable Rust benchmark framework, configured as a dev-dependency with a custom harness ([Divan docs](https://docs.rs/divan/latest/divan/)). It has the same policy cost as Criterion and offers no needed advantage for the current absence of a performance target.
- **iai-callgrind:** Measures instruction/cache-related events through Callgrind rather than relying solely on wall-clock duration, but requires the external Valgrind/Callgrind toolchain as well as its Rust package ([iai-callgrind docs](https://docs.rs/iai-callgrind/latest/iai_callgrind/)). Its additional setup is not justified for this small CLI without a demonstrated need for lower-noise profiling.

## Useful Boundaries and Inputs

The project currently has one binary target and no library target ([`Cargo.toml`](../../Cargo.toml)). Parsing and rendering are internal functions in [`src/main.rs`](../../src/main.rs), while the CLI integration tests launch the compiled executable ([`tests/cli_to_svg.rs`](../../tests/cli_to_svg.rs)). This gives a clean end-to-end boundary today, but an independent parser or renderer benchmark would require an internal test or module/API change. Do not restructure the product solely to create benchmarks.

If profiling later warrants component measurements, keep the boundaries separate:

1. **Parser:** in-memory MusicXML bytes to a parsed score; exclude fixture loading and score generation.
2. **Renderer:** a prebuilt score to SVG text; exclude parsing and input generation.
3. **End to end:** a fresh release CLI process from input path to completed SVG, including startup and file I/O. This is the most practical first boundary and answers user-visible latency, but cannot attribute the cost to a component.

Use existing valid fixtures as distinct cases: [`minimal.musicxml`](../../tests/fixtures/minimal.musicxml) for a small smoke input, [`canonical.musicxml`](../../tests/fixtures/canonical.musicxml) for the representative score, and [`multi-octave-beaming.musicxml`](../../tests/fixtures/multi-octave-beaming.musicxml) for a more involved engraving case. If scaling behavior becomes important, add a deterministic family of valid repeated-score inputs at documented sizes; keep fixture construction outside the timed region and record bytes and score/event counts. Do not use malformed inputs as ordinary throughput cases because the early-error path measures a different workload.

## Method and CI

For the optional local baseline, build once with `cargo build --release`, then use a small throwaway `std::time::Instant` driver to spawn the release executable directly. For each fixture, do one unmeasured warm-up and about 30 measured process launches; report the median and median absolute deviation, along with the raw sample count. Keep the output path, command, machine, and cache conditions consistent. Record the Rust toolchain, target, revision, fixture hash/size, and whether file-system caches are warm. This measures end-to-end latency only. Do not include compilation in the timed region, and do not treat one run or a minimum time as a stable result. The explicit warm-up and repeated-sample approach mirrors the controls offered by Criterion, without adding it to the repository ([Criterion warm-up](https://bheisler.github.io/criterion.rs/book/user_guide/warm_up_time.html)).

Wall-clock results remain sensitive to host load, scheduling, CPU power/thermal state, and cache state; repeated measurements reduce but do not remove those effects. Keep correctness tests in ordinary CI. If the project later needs performance tracking, start with scheduled or manually triggered runs on a controlled, documented runner and publish trends; first establish run-to-run variation before setting a threshold. Avoid pull-request failures based on noisy shared-runner timings. A benchmark smoke test can verify that a benchmark still runs, but should not be confused with a regression gate.

**Smallest useful baseline:** no committed suite now. When an actual performance question appears, time one representative end-to-end release invocation with the std-only repeated-process method above. Add parser and renderer cases only if that result or a profiler identifies a component worth tracking; if dependency policy is then relaxed, prefer Criterion over maintaining a custom statistical harness.
