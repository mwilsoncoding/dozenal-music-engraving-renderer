# Research: LilyPond and MuseScore horizontal spacing

Status: comparative research only. This report does **not** change the renderer specification or adopt spacing rules. MVP scope: one part/voice, three-line dozenal notation, no accidentals, self-contained SVG, one unconstrained-width system, no scaling/system breaks, and no third-party Rust dependencies.

## Sourced facts

### Rhythm and event spacing

- **LilyPond:** `calc_common_shortest_duration` finds the shortest note in each measure, then uses the most frequent such duration, capped by `base-shortest-duration` (default 1/8 in this code path). `Note_spacing::get_spacing` starts from an ideal spring distance, adjusts it for the left notehead extent, and returns a spacing spring. Spacing is therefore duration-sensitive and elastic, not a fixed x-step per event. The manual discusses spacing adjustments and proportional spacing, which are broader engraving controls than this MVP needs. See [LilyPond spacing source](https://github.com/lilypond/lilypond/blob/e01b9d8b7d4fc0d8a3ca033c74d2bbbeeeb85cfd/lily/spacing-spanner.cc#L84-L178), [`note-spacing.cc`](https://github.com/lilypond/lilypond/blob/e01b9d8b7d4fc0d8a3ca033c74d2bbbeeeb85cfd/lily/note-spacing.cc#L74-L116), and the [Spacing issues manual](https://lilypond.org/doc/v2.25/Documentation/notation/spacing-issues.html).
- **MuseScore:** `computeSegmentDurationStretch` uses segment ticks and shortest chord/rest duration, with separate handling for adjacent chord/rests and polyrhythmic timing. `chordRestSegmentNaturalWidth` multiplies duration stretch by a base containing notehead width plus the style's minimum note distance. This is a duration-derived natural width that is later subject to layout stretching/squeezing. See [`horizontalspacing.cpp`](https://github.com/musescore/MuseScore/blob/ac9d3bcd3df7a19d16d7ef505db9e2b54235c022/src/engraving/rendering/score/horizontalspacing.cpp#L675-L728). The official [horizontal-spacing handbook](https://musescore.org/en/handbook/4/systems-and-horizontal-spacing) documents user controls such as stretch; it is not a specification of the internal weighting formula.

### Note/chord extents and minimum clearance

- **LilyPond:** the note-spacing implementation uses the left notehead's horizontal extent and skyline distance. The minimum spring distance is set from the skyline separation, including the configured vertical padding; the ideal distance remains a distinct value. The spacing-spanner also adds skyline-based rods between columns to protect overhangs. Thus visible shapes affect both ideal placement and minimum clearance. See [`note-spacing.cc`](https://github.com/lilypond/lilypond/blob/e01b9d8b7d4fc0d8a3ca033c74d2bbbeeeb85cfd/lily/note-spacing.cc#L74-L116) and [`spacing-spanner.cc`](https://github.com/lilypond/lilypond/blob/e01b9d8b7d4fc0d8a3ca033c74d2bbbeeeb85cfd/lily/spacing-spanner.cc#L232-L319).
- **MuseScore:** `minHorizontalDistance(Shape, Shape, ...)` compares pairs of shape elements whose vertical intervals intersect after vertical clearance. It computes padding per element pair, with an implementation-specific absolute lower bound of `0.1 * spatium * squeezeFactor`, then derives horizontal separation from their left/right bounds. This is not a universal note-to-note gap: it is conditional on the shape elements, their vertical relation, item padding, and style. See [`horizontalspacing.cpp`](https://github.com/musescore/MuseScore/blob/ac9d3bcd3df7a19d16d7ef505db9e2b54235c022/src/engraving/rendering/score/horizontalspacing.cpp#L1118-L1156).
- In either implementation, “chord extent” is rendered geometry, not only duration. For this MVP, the transferable geometry is the union of the custom tone glyphs and attached stems, dots, flags/beams, or other supported marks. Accidental-specific spacing is deliberately not relevant because accidentals are excluded.

### Measure widths and barlines

- **LilyPond:** rhythmic/non-rhythmic paper columns are connected by springs, while skyline rods constrain minimum separation for overhangs. Measure boundaries participate in the column layout, but the cited mechanisms do not imply that measure width is merely a sum of notehead widths or that every bar receives the same width. The [Bars manual](https://lilypond.org/doc/v2.25/Documentation/notation/bars.html) describes barlines as measure delimiters and documents carry-over behavior; automatic line breaking and line fitting are outside this MVP.
- **MuseScore:** `computeMinMeasureWidth` starts from a style minimum, accounts for the first chord/rest segment's position and either bar-note or bar-accidental distance, then `enforceMinimumMeasureWidths` stretches a measure when needed. Its full-system layout can further justify/squeeze spacing, which this MVP excludes. See [`horizontalspacing.cpp`](https://github.com/musescore/MuseScore/blob/ac9d3bcd3df7a19d16d7ef505db9e2b54235c022/src/engraving/rendering/score/horizontalspacing.cpp#L917-L969) and the official [Measure properties handbook](https://musescore.org/en/handbook/4/measure-properties).
- **LilyPond barline interaction:** non-musical right columns can be spaced to the barline extent rather than the start of the column when `space-to-barline` applies; the code also retains at least part of the note-column gap. See [`note-spacing.cc`](https://github.com/lilypond/lilypond/blob/e01b9d8b7d4fc0d8a3ca033c74d2bbbeeeb85cfd/lily/note-spacing.cc#L87-L115). The exact policy depends on column type and properties.
- **MuseScore barline interaction:** end-barline layout chooses normal versus final barline type, can suppress a barline before a repeat start in a specific context, and aligns barline widths across staves. Barline segments also flow through horizontal spacing; selected barline-to-barline and barline-to-multi-measure-rest cases have explicit minimum-distance handling. Those special cases are not the MVP's simple single thin measure-end barline. See [`measurelayout.cpp`](https://github.com/musescore/MuseScore/blob/ac9d3bcd3df7a19d16d7ef505db9e2b54235c022/src/engraving/rendering/score/measurelayout.cpp#L1446-L1480) and [`horizontalspacing.cpp`](https://github.com/musescore/MuseScore/blob/ac9d3bcd3df7a19d16d7ef505db9e2b54235c022/src/engraving/rendering/score/horizontalspacing.cpp#L1174-L1223).

## Transferable recommendations (not adopted rules)

These are candidates for later review, not decisions or requirements:

1. Retain onset timing and duration when assigning x positions. A deterministic duration-derived preferred advance avoids equal spacing for unequal rhythms.
2. Separately compute the geometric minimum from the actual custom SVG extents and a chosen clearance. Compare neighboring supported onset shapes only where their vertical extents can collide; do not borrow either project's numeric padding as a dozenal engraving rule.
3. Include all supported simultaneous chord glyphs and attached rhythm marks in the onset's geometry. No accidental/clef reservations are needed for this MVP.
4. Treat each measure-end barline as boundary geometry with explicit note-to-barline clearance. The existing MVP decision requires a barline at each measure end, including the final end; it does not require opening, double, or repeat barlines.
5. Solve one unconstrained system and let SVG width grow. Do not import line breaking, page fitting, system justification, or scaling behavior.

## Non-transferable concepts and uncertainty

- LilyPond's paper-column/grob/spring system and MuseScore's style-rich segment, skyline/shape, collision, and page-layout machinery are implementation details, not specifications for a small Rust SVG renderer.
- Neither source establishes metrics for hand-drawn dozenal glyphs, a three-line staff, or this renderer's SVG coordinate system. The cited MuseScore `0.1 spatium` minimum is specifically an internal spacing lower bound in its own coordinate/style model, not a recommendation for this project.
- The comparison is source-based, not a controlled visual benchmark; no common score was rendered in both programs. Exact preferred advances, glyph clearances, and barline padding remain design questions. This report deliberately adopts none of them.

No renderer code, implementation specification, GitHub issue, or pre-existing fixture was modified. The report itself is the only new file.
