# Rust Snapshot Testing for SVG Output

## Recommendation

**Avoid a crate-backed snapshot workflow for the MVP; defer reconsidering Insta until the dependency constraint changes.** The README says `Dependencies: None`, and the accepted MVP specification prohibits third-party Rust crates and explicitly requires testing without them. Cargo classifies dev-dependencies as test/example/benchmark dependencies, but they are still third-party crates needed to compile those targets. Insta as a dev-dependency therefore does not fit the current rule, even though it would not be a runtime dependency. [README](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/blob/22d7caa/README.md), [MVP issue #21](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/21), [Cargo dev-dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#development-dependencies)

Issue #7 proposed structural/layout assertions plus a reviewed raster snapshot through a pinned PNG pipeline. The later MVP decision keeps semantic and layout assertions as the SVG acceptance gate and explicitly defers raster snapshots with PNG output. That later decision controls this MVP; no raster pipeline or raster snapshot is needed for the current self-contained SVG-only contract. [Issue #7](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/7), [MVP issue #21](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/21)

## Current Coverage

At repository revision `22d7caa`, the tracked fixtures are MusicXML inputs, not checked-in SVG goldens. The CLI integration tests assert output-path behavior, SVG structure and styling, glyph presence, and concrete layout invariants such as event spacing, collision clearance, stem direction, and barline placement. These targeted checks explain failures in domain terms and match the MVP's specified structural/layout gate; replacing them with whole-document snapshots would lose that specificity. [CLI tests](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/blob/22d7caa/tests/cli_to_svg.rs), [tracked fixtures](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/tree/22d7caa/tests/fixtures), [MVP issue #21](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/21)

## Insta Compared with SVG Goldens

Insta offers a useful workflow: failed snapshots are written as `.snap.new`, `cargo insta review` supports interactive approval, and `INSTA_UPDATE` can disable updates or explicitly overwrite snapshots. Its docs say CI behavior depends on `CI` being set; using `INSTA_UPDATE=no` makes the no-write intent explicit. `cargo-insta` improves review ergonomics but is optional. These safeguards and readable diffs are real benefits, but add a crate, lockfile/dependency maintenance, and optional local tooling to a project that forbids test crates. Insta is Apache-2.0 licensed, which is permissive, but does not resolve the project-policy conflict. [Insta quickstart](https://insta.rs/docs/quickstart/), [snapshot files](https://insta.rs/docs/snapshot-files/), [Insta license](https://github.com/mitsuhiko/insta/blob/master/LICENSE), [Cargo dev-dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#development-dependencies)

The renderer serializes its scene to SVG path strings in a fixed command order, with explicit formatting for numeric coordinates; it does not rasterize the SVG or rely on host fonts. A string snapshot would therefore compare renderer output, not viewer pixels, and avoid platform differences introduced by an SVG renderer. Exact snapshots would nevertheless flag any serialized change, including benign formatting or intentional geometry changes. Insta normalizes snapshot-file newlines and offers configurable string filters, but filters can also hide meaningful output changes if too broad. No project-level promise of byte-identical output across Rust toolchains is stated, so cross-toolchain stability should not be assumed without a check. [SVG serializer at revision 22d7caa](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/blob/22d7caa/src/main.rs), [Insta snapshot files](https://insta.rs/docs/snapshot-files/), [Insta filters](https://insta.rs/docs/filters/)

A standard-library alternative is a reviewed `.svg` golden beside the existing MusicXML fixture, compared with `include_str!` and `assert_eq!`. It adds no crate and can be updated by rendering the fixture and reviewing the ordinary Git diff. It has less specialized diff/review tooling than Insta and the same whole-document sensitivity, so it should supplement—not replace—the semantic/layout assertions. Since the current tests already cover the specified invariants and the MVP does not require byte-for-byte SVG baselines, adding a golden is not justified yet.

## Smallest Future Step

No snapshot rollout is justified under the current constraints. If the project explicitly relaxes the no-crate rule and requests serialized-output regression coverage, start with one canonical SVG snapshot while retaining all semantic/layout assertions; keep raster snapshots deferred. Pin the Insta version, review updates rather than auto-accepting them, and run CI with `CI=true` and `INSTA_UPDATE=no`. Otherwise, a single standard-library golden is the smaller dependency-free option if exact SVG serialization becomes a stated requirement. [Insta quickstart and CI behavior](https://insta.rs/docs/quickstart/#continuous-integration), [MVP issue #21](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/21)
