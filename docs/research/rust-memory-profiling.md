# Rust Memory Measurement and Profiling

Research for [issue #52](https://github.com/mwilsoncoding/dozenal-music-engraving-renderer/issues/52). The [Rust Project Primer memory guide](https://rustprojectprimer.com/measure/memory.html) is a useful starting overview; implementation and tool claims below are checked against primary documentation.

## Project Context

The README sets `Dependencies: None`; the MVP also rejects external resource resolution and caps input at 64 MiB. The reader accepts at most the limit plus one byte to detect overflow, and the XML processor separately caps aggregate entity expansion at 8 MiB ([README](../../README.md), [XML reader](../../src/xml.rs)).

The 64 MiB input boundary is worth measuring. During UTF-8 decoding, `Source::decode` retains the input while building `Vec<(char, usize)>`, a normalized `String`, and a byte-offset `Vec<usize>` ([decoder](../../src/xml.rs)). On a typical 64-bit Linux build, an ASCII input near the limit implies roughly 1.6 GiB of live payload across those four representations (assuming a 16-byte tuple), before vector capacity slack, the parsed element tree, and SVG output. This is a source-based estimate, not an observed RSS result; it makes peak RSS the first useful measurement. The entity-expansion cap addresses a distinct input-amplification path.

## Options

- **Peak RSS, std/dependency-free:** GNU `/usr/bin/time -v` reports a child process's maximum resident set size ([GNU manual](https://www.gnu.org/software/time/manual/time.html)); Linux also exposes `VmHWM` as peak RSS in `/proc/<pid>/status` ([kernel documentation](https://docs.kernel.org/filesystems/proc.html#proc-pid-status)). RSS measures resident process memory, not just Rust heap allocations. Use `/usr/bin/time` explicitly because `time` implementations and output differ.
- **Heap allocation diagnosis:** Heaptrack records allocation events and supports post-run analysis; its upstream describes it as a Linux profiler with low overhead ([project README](https://github.com/KDE/heaptrack/blob/master/README.md)). Valgrind Massif profiles heap growth over time, while DHAT analyzes allocation size, lifetime, and use ([Massif manual](https://valgrind.org/docs/manual/ms-manual.html), [DHAT manual](https://valgrind.org/docs/manual/dh-manual.html)). These instrument execution and perturb it; use them to explain a regression, not as the source of production-like RSS or timing numbers. Their availability also depends on the Linux image and target architecture.
- **Rust-only instrumentation:** Rust's `GlobalAlloc` permits a custom counting allocator, but it is an unsafe allocator implementation hook, not a standard RSS or heap-profiler API. It can count allocator requests routed through the global allocator, not process RSS; instrumentation adds complexity and can perturb allocation behavior ([Rust `GlobalAlloc`](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html)). It is not the simplest baseline here.
- **`perf`:** Linux `perf` is useful for CPU/hardware-counter sampling, but is not a direct peak-RSS or per-allocation profiler; permissions and available counters vary by kernel and runner ([`perf_event_open`](https://docs.kernel.org/userspace-api/perf_event_open.html)). It is not needed for the first memory check.

## Recommendation

**Adopt a small RSS measurement now; defer an allocation-profiler dependency and any hard CI threshold.** Build the binary before measurement, then run the same release binary and fixed inputs under `LC_ALL=C /usr/bin/time -v`. Include the canonical fixture, a valid accepted score just below 64 MiB with little semantic content, and an input exercising entity expansion rejection. Keep input and output paths fixed and record the binary/profile, fixture hashes, runner image, kernel, GNU time version, and each run's result. Repeat several times on the same Linux runner and compare distributions; first establish a baseline, then decide whether a generously slackened regression threshold is stable enough for CI. Do not compare RSS values from different runner images or profiled versus unprofiled executions. Cargo's profile settings affect the binary, so keep the selected profile fixed ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)).

GNU time, Valgrind, and Heaptrack are **external developer/CI tools**, not Rust runtime dependencies and not additions to Cargo's dependency graph. Their licenses apply to the tools themselves: GNU time is GPL-3.0-or-later ([license](https://git.savannah.gnu.org/cgit/time.git/plain/COPYING)); Valgrind's core is GPL-2.0-or-later, with some separately licensed components ([license information](https://valgrind.org/info/opensource.html)); Heaptrack is GPL-3.0-or-later ([license](https://github.com/KDE/heaptrack/blob/master/COPYING)). `dhat` is a Rust crate with `MIT OR Apache-2.0` terms ([crate documentation](https://docs.rs/dhat/latest/dhat/)), but even a dev-only crate would add a third-party Rust dependency and conflict with the current MVP rule. External tools installed on a developer machine or CI image do not change that Cargo policy; review redistribution obligations if the project ever bundles a tool.

When an RSS run confirms a regression or identifies the near-limit path as too costly, use Heaptrack or Massif locally to find allocation sources, and DHAT when allocation lifetimes are the question. Keep that work opt-in; the present evidence justifies measuring the existing boundary, not permanently instrumenting the renderer.
